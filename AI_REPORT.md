# Mandatory AI Usage Report

**AI TOOL USED:** ChatGPT

**WHAT I ASKED AI TO DO:**
1. Help me break down the Student Support & Ticket Management problem into clear Student, Staff, and Manager workflows, including ticket lifecycle, ownership, SLA handling, escalation, and activity tracking.
2. Help me refine the product and technical approach step-by-step, including API structure, role-based dashboards, ticket state transitions, SLA rules, pending-student workflows, and important edge cases.
3. Review parts of my implementation during development, identify potential issues, suggest improvements, and help validate the completed workflows through practical testing scenarios.

**PROMPT THAT WAS MOST USEFUL:**
> "Think of the three panels as having the same design system, but different information density and purpose. Student panel should feel simple and friendly. Staff panel should look similar to Student, because both are operational/product interfaces. The Manager panel should focus more on operational monitoring and management visibility."

**CODE GENERATED BY AI: What part?**
ChatGPT was used to assist with implementation ideas, code snippets, component structures, API patterns, validation logic, and debugging during development. The suggestions were adapted to the project's existing structure and requirements rather than being directly used as the final implementation.

**CODE I MODIFIED: What part?**
I made the final implementation decisions and modified the suggested approaches according to the application's requirements. This included the ticket state machine and valid status transitions, SLA and pending-student behavior, role-specific dashboard workflows, assignment/reassignment logic, activity tracking, and UI behavior.

I also manually tested the implementation and adjusted the code whenever the actual application behavior differed from the intended workflow.

**AI OUTPUT THAT WAS WRONG:**
During development, some initial approaches did not fully match the application's intended business workflow. For example, an initial SLA-health approach could treat tickets that were no longer operationally active as part of the active SLA workload.

**HOW I IDENTIFIED THE PROBLEM:**
I compared the suggested implementation against the defined ticket lifecycle and manually tested the workflow using different ticket statuses. This showed that SLA health should represent tickets that still require operational action rather than resolved or closed tickets.

**HOW I FIXED IT:**
I refined the implementation so that SLA health is calculated using only active ticket states: `OPEN`, `ASSIGNED`, `IN_PROGRESS`, and `PENDING_STUDENT`.

I then tested the workflow again with different ticket states and verified that resolved and closed tickets were removed from the active SLA health calculation.
